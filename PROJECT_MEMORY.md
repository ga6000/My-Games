## Project overview

**Vision:** A small hub of browser-playable game prototypes for a ~3-10 person friend group,
served as static files from GitHub Pages, with an increasing share supporting shared
multiplayer rooms.

**Real stack (not the generic template stack):**
- Frontend: vanilla JavaScript + HTML5 Canvas, one self-contained `.html` file per game
- Multiplayer: raw `ws` WebSocket server (`gyro-space-server-main/server.js`), **not** Socket.IO
- Persistence: **Firestore** (not Realtime Database) via `firebase-config.js`, shared by
  `leaderboard.html` and `gyro-space/space-tracer.html`
- Hosting: GitHub Pages (repo `ga6000/My-Games`) for the games; Render (free tier) for the
  WebSocket server, deployed from the separate `gyro-space-server` repo
- No build step, no bundler, no npm runtime deps in the browser — `package.json` here is
  dev-only tooling (the collision checker), never shipped to the client

**Folder layout (as of the 2026-08-24 restructure):** each game lives in its own top-level
folder at the repo root (`gyro-space/`, `javelin-battle/`, etc.) with its original filename
kept. `index.html`, `leaderboard.html`, and `firebase-config.js` stay at the repo root as
shared hub-level infrastructure. There is no `games/`, `docs/`, `src/`, or `archive/`
subfolder structure — that was an artifact of docs generated against a different project.

### Multiplayer architecture in one line
One shared server, rooms namespaced `game:code`, a **generic `relay` message** so new games need
zero server changes, plus server-issued **room seeds** (the thing that makes every client build
the same world) and **host election** for games that actually have shared state. Client side is
one shared file, `shared/mp-core.js`, exposing a single global `MP`.

## Technical debt

### ✅ RESOLVED 2026-09-03 — Colour/identity is centralized in `shared/identity.js`

**AUTHORITY** was resolved 2026-08-24: the server computes colour from the player name and sends
it back; clients use what they're given, via `MP.selfColor`. That part was always true.

**DUPLICATION was not**, and the Option A/B decision recorded below sat open until 2026-09-03.
The audit found **four** client-side implementations, not the two it warned about:

| Where | What it was |
|---|---|
| `server.js` | the authority |
| `index.html` | byte-identical copy, used as a fallback in **9** call sites |
| `reality-rewrite.html` | a **different scheme** — `nameHash(name) % 360` → an hsl hue, not the palette |
| `space-tracer.html` | a **third palette**, of which only `[0]` was ever read — so every unknown ship rendered **red** |

Measured before the fix: **reality-rewrite agreed with the server 0 times out of 10.** And it
could never self-correct, because it preferred `?color=` from the URL while `gameHref()` only
ever passes `?name=` and `?room=`.

**Neither Option A nor Option B as written was achievable, and that is the useful part.** Option A
("server computes it, clients hold nothing") is impossible here: `file://` play is a hard
constraint, a double-clicked game has no server, and it still has to colour its players. **The
client copy is required.** So duplication here cannot be designed away — only made safe.

What shipped is Option B done properly, plus the piece that was missing from both options:

- **One** client implementation, `shared/identity.js`, exposing a single global `IDENTITY`.
  Loaded by the hub and all six mp-core games. The other three copies are deleted.
- **`scripts/check-identity-parity.js`** compares it against `server.js` across 3,000+ names
  including empty, whitespace, unicode and case variants, and fails on drift. Verified against a
  control: shifting **one** palette entry by **one degree** is caught (204 of 3,025 names change).
  This is what makes the mandatory duplication safe, and it is the thing neither option had.
- **Palette widened 10 → 16** at the same time, because the old one had a real defect — see below.
- `mp-core`'s solo path now seeds `MP.selfColor` from `IDENTITY`, so a `file://` player gets
  *exactly* the colour the server would have given them. Reconnecting never changes it.

### The old palette had two indistinguishable yellows

Hues **45 and 50**, five degrees apart. Minimum pairwise CIE76 ΔE of **9.7**, which is inside
"easily confused". So two players with **different** colours could look identical — worse than a
plain collision, because nothing signals it and neither player is doing anything wrong.

Replaced with 16 hues at 22.5° spacing, saturation and lightness **solved rather than picked**:
a hill-climb maximising the minimum ΔE, constrained so every colour keeps ≥1.9:1 contrast against
**both** grounds this repo draws on — `#0D1117` (most games) and near-white (glucose-dash's mall,
and reality-rewrite's `#f4f6f8`). Result: **minimum ΔE 25.9** (2.7× better), worst contrast 1.90:1
on white and 1.92:1 on dark.

**Collisions are reduced, not eliminated, and that is worth being honest about.** 16 buckets and
10 players is still a birthday problem: ~97% chance of at least one shared colour at 10 players,
down from 100% at 10 colours. What the fix *does* guarantee is that two **different** colours are
never confusable. Eliminating collisions outright needs per-room deflection (assign the hashed
colour, step to the next free one if taken), which would break "same name → same colour, always"
— a deliberate property of the current design. **Not done; flagging the trade rather than
silently making it.**

The original problem statement is kept below for context.

### (Historical) Color/identity hash was client-side, not server-side

Root `CLAUDE.md`'s hard constraints say color/identity assignment is "server-side, name-hash
based." **The actual implementation is client-side**: both `index.html` and
`gyro-space/space-tracer.html` independently run the same djb2-style hash in JS and send the
resulting color to the server in the `join-room` message; `server.js` just does
`if (data.color) player.color = data.color;` — it trusts whatever it's given, it doesn't
compute anything itself.

**Why this matters for the rollout:** every new game that joins a room needs this same
palette + hash function. Right now that logic is duplicated (and could silently drift) between
two files. Before wiring up the pilot game, decide:
- **Option A — make it actually server-side:** server computes color from `name` on join,
  ignores/discards any client-sent color. Matches the documented constraint exactly; one
  source of truth; no per-game duplication possible.
- **Option B — keep it client-side but centralize it:** extract `COLOR_PALETTE` +
  `hashStringToIndex` + `getColorFromName` into one shared script (e.g. `identity.js` at repo
  root) that every game's HTML includes via a classic `<script src="../identity.js">` tag, and
  update root `CLAUDE.md`'s hard constraint to describe reality instead of the aspiration.

~~Not decided yet — flagging for the next planning pass, before the pilot game starts.~~
**Decided and shipped 2026-09-03** — see the RESOLVED entry above. Neither option as written was
achievable: Option A is impossible under the `file://` constraint, and Option B alone had no
protection against the client and server drifting apart. What shipped is Option B **plus a parity
check**, which is the part both options were missing.

### ✅ RESOLVED 2026-09-02 — `zombie-endgame.js` was loaded twice in `Zombie.html`

Found during the 2026-09-02 doc audit and fixed the same day. `Zombie.html` carried
`<script src="zombie-endgame.js">` on **both line 257 and line 258**.

Top-level `const`/`let` declarations are shared across classic `<script>` tags in one page, and
that file has 22 of them, so the second copy threw
`SyntaxError: Identifier 'ROLES' has already been declared` in the console on **every load**.
The duplicate tag was discarded whole at instantiation, so nothing was double-initialised and
the game played normally — a console error and a loading-order landmine, not a crash.

**Fixed by deleting the repeated line.** Load order is now mp-core → core → audio → level →
entities → endgame → game → net → render. A scan of all 20 HTML files in the repo (including
`hex-grid/Hex Grid.html`, whose space in the filename defeats a naive shell loop) found no other
page listing any `src` twice.

**The more useful outcome: `check-global-collisions.js` now catches this class of bug.** It
previously could not — and the reason is worth keeping, because it was not an oversight in the
comparison logic but a silent `[...new Set(srcs)]` in `extractLocalScriptSrcs`. The repeated tag
was **deduped away before any analysis ran**, so the page reported
`OK  zombie\Zombie.html (9 local scripts)` — a count that was itself already deduped — while the
browser threw on every load. A checker that quietly normalises its input cannot see defects that
live in the input.

The check now reports duplicates with the severity that actually applies:
- any top-level `const`/`let`/`class` in the repeated file → `SyntaxError on load`, naming the
  first identifier that collides
- only `var`/`function` → `file executes twice (top-level side effects re-run)`, which is the
  quieter and arguably nastier case

Verified against a control: reintroducing the duplicate in a throwaway copy produces
`⚠ duplicate <script src>: 'zombie-endgame.js' — listed 2×` with **exit code 1**, and a single
listing of the same file still passes clean.

⚠️ **Note the exit code currently buys nothing at commit time.** `.githooks/pre-commit` runs the
checker as `node scripts/check-global-collisions.js || true` — warn-only by design, so it prints
the warning and **always exits 0**. Its own comment says to drop the `|| true` "once you've run it
against the real repo a few times and trust it." That has not been done. A duplicate `src` (or any
collision) will be *reported* by the hook but will **not** block the commit.

**Still not detected: duplicate definitions *within* one file** — the checker compares across
files and never compares a file to itself. That is what hid Glucose Dash v4's duplicate `quad()`,
and splitting a game into multiple files remains what makes those visible. Two of this repo's
duplicate-definition bugs have now survived a green checker; this closes one of the two shapes.

### `firebase-config.js` needs http(s), which conflicts with the file:// hard constraint

Root `CLAUDE.md` requires games to run via double-click (`file://`, no server). But
`space-tracer.html` and `leaderboard.html` load `firebase-config.js` via
`<script type="module">`, which browsers refuse to load over `file://`. In practice this means:
opened locally by double-click, Gyro Space and the leaderboard still load and mostly work, but
no score is saved until the page is served over http(s) (GitHub Pages, or a local
`python -m http.server`).

**Corrected 2026-08-31:** this entry used to say the failure was silent ("no console-visible
crash, just no score saved"). It wasn't. `reportLifeEnded()` called the global
`submitScoreToFirebase(...)` bare, and over `file://` that global never exists, so **every
death threw a `ReferenceError` out of the middle of that function** — skipping the live score
relay to the room and the per-life counter resets that follow the call. Now guarded with
`typeof submitScoreToFirebase === "function"`. Worth generalising: a `window.x = ...` set from
a `type="module"` block is not a safe bare call from a classic script, because the two have
completely different load-failure modes — `typeof` is the only check that survives the
identifier never being declared at all.
This is an accepted, working tradeoff today — noting it here so it's not "discovered" again as
a surprise bug during the multiplayer rollout, since every newly-integrated game will hit the
same constraint if it also wants Firestore leaderboard support.

### Three hub features were dead in production (fixed 2026-08-24)

Found while restructuring the server. `index.html` had been sending `vote-update` and
`cursor-update` since the group-play panel was added, and expected a `votes` snapshot on join —
**the server had no handler for any of them.** The vote checkmarks and live cursors did nothing
in production. Separately, the server's `leave` message omitted `name`, but the hub's leave
handler keys off the name, so departed players were never removed from the roster despite a
code comment claiming they were. All four are now implemented and covered by tests.

The lesson worth keeping: `index.html` carried detailed comments describing behaviour that
could not happen. Comments describing a protocol are not evidence the other side implements it —
check both ends.

### The room roster was a dead end on every phone (fixed 2026-08-28)

`#roomRoster` was a fixed-position sidebar: `right:0; width:240px; height:100vh`, widened to
`width:100%` under 768px while keeping `height:100vh`, with the content-offset padding applied
only at `min-width:769px`. On any narrow viewport, **joining a room covered the entire games
list with an opaque panel whose only control was "Change name / room."** There was no way
forward to the games at all. Desktop was unaffected, which is why it shipped.

Two related defects went with it: the roster never listed *you* (the server's `players`
snapshot excludes self and sends it separately as `you`; the hub never added itself back, and
the `.roster-player-you` style was dead), and the Zombie card carried Space Tracer's rocket icon.

Worth generalising: **a fixed-position panel that goes full-bleed at a breakpoint needs a way
out at that breakpoint.** The replacement is a top band, which can't cover anything.

## Recurring technical challenges (real, observed in this repo)

### No game generated a deterministic world (partially fixed 2026-08-24)
Every game built its world with unseeded `Math.random()`, including `space-tracer.html` — whose
`seedAsteroidField()` takes no seed, meaning **every player in a Gyro Space room right now is
flying through a different asteroid field.** That's survivable there (asteroids are scenery) but
fatal anywhere the world is the game. Fixed for Zombie via the server-issued room seed +
`MP.random()`; still outstanding for every other game.

### A reference to a name nothing declares is invisible until a rare path runs (found 2026-09-07)
`zombie-game.js`'s `relocateZombie()` read `SPAWN_RING_MIN` and `SPAWN_RING_MAX`. **Neither
existed anywhere in the repo.** Nothing caught it: there is no bundler, no type checker, and
`check-global-collisions.js` looks for *duplicate* declarations, not missing ones. A
`ReferenceError` is a runtime error, and this one lived on the escape hatch for a zombie the
steering could not free — so it only fired once a big zombie actually wedged, which is exactly the
condition that most needed the escape hatch.

When it fired, the throw propagated out of `updateZombies` and killed the rest of `update()` on
the host: revives, traps, and **`broadcastPlayers` / `broadcastWorld`**. `gameLoop` re-arms its
rAF first (deliberately, so a transient error survives one frame), so the host kept drawing and
looked healthy while every other client in the room froze. And because the throw landed before
`z.stuck = 0`, it repeated every frame forever. One wedged brute silently ended the session for
everyone.

**`scripts/check-undefined-globals.js` now closes this**, and is in the pre-commit hook. It is the
complement to the collision checker: that one asks "did two files declare the same top-level
name?", this one asks "did a file reference a name no script on the page declares?". It resolves
against every script that loads together on a page (they share one global scope), `window.X`
publishes including the repo's `global.X` alias idiom, enclosing lexical scopes, a browser+Node
builtin list, and any name the file itself feature-detects with `typeof X` (an optional
dependency, which mp-core uses on purpose). A page that loads a CDN script is reported **WARN**
rather than FAIL — its globals are not visible, so its findings are unproven and must not fail a
commit. Currently: clean everywhere except three `under-development/` three.js pages, correctly
warned. Regression-tested by reintroducing the phantom constants; it catches them.

**The general lesson:** in a repo whose hard constraint rules out modules and bundling, nothing
but a checker will ever tell you about a misspelled global, and the ones that hurt live on paths
that only run when something has already gone wrong.

### A reconnect can hand back a NEW room seed, and rebuilding the world on it destroys the run (fixed for Zombie 2026-09-07)
The other half of the same session's report: "the map regenerates entirely, mid-game, ten rounds
in — every door shut again and a new layout."

`mp-core` fires `onPeerSync` from **every** `players` message the server sends — join, leave, and
the rejoin handshake — and applies `setSeed(data.seed)` on the line immediately before. Zombie's
handler ended with an unguarded `if (MP.seed() !== levelSeed) generateLevel();`, which clears
walls, doors, barricades, wall-buys, crates, barrels, traps, zone cooldowns and the endgame chain.
The server hands back a different seed whenever the room was garbage-collected while everyone was
briefly disconnected and then recreated on rejoin — and since `mp-core` reconnects on a 3s timer
after every `onclose`, a sleeping free-tier instance or a sleeping laptop produces that routinely.

Note this is the **same hook** as the entry below, doing the same job correctly for a different
case: a client that missed the 6s timeout genuinely does need to rebuild once the room seed lands.
The two cases cannot be distinguished by looking at the seed. The fix is to gate on whether the
game is running (`gameStarted`), and to make the **host authoritative over the geometry seed** by
publishing `ls: levelSeed` on the world snapshot — one integer on a packet already shipping 15×/s,
riding the generic `relay`, asking nothing of the unchangeable server. **Any game that builds its
world from `MP.seed()` and regenerates on a seed change has this bug.** Zombie is the only one
that does today.

### A one-shot `onReady` can't cover a connection that arrives late (fixed for Zombie 2026-09-01)
`mp-core` starts the game solo if the socket hasn't opened in `CONNECT_TIMEOUT_MS` (6s) and
keeps retrying in the background, "promoting" the player to multiplayer if it connects later.
But `onReady` fires **exactly once**, so everything a game sets up there — its net id, its
host flag, and any world built from the seed — is permanently stuck at the solo values on that
path. Render's free tier cold-starts in tens of seconds, so this is the *ordinary* experience
for whoever opens the game first, not a rare race.

For Zombie this meant a promoted client kept `netIsHost = true` (the solo fallback) and went on
spawning zombies and broadcasting world snapshots **alongside the real host** — two authorities
on one arena — while still identifying as `solo:<ctrl>`, so two cold-started clients shared an
id and `isMyNetId()` made each refuse to render the other's players. Its walls also stayed on
the throwaway clock seed: the exact "two players collide with walls the other cannot see" defect
`mp-core` exists to prevent.

**The hook to resync on is `onPeerSync`, not `onStatus`.** `onStatus` is fired by the *first
line* of mp-core's `players` branch, before that same message's `id`, `hostId` and `seed` have
been applied — a game resyncing there reads a null id and a stale seed. `onPeerSync` fires at
the end of the branch, after all three. Gate any world rebuild on the seed actually having
changed, so a plain reconnect to the same room doesn't drop a fresh building on a standing
player.

**Every other game on `mp-core` should be audited for this** — anything that reads
`info.selfId`, `info.isHost`, or `info.seed` inside `onReady` and never revisits it has the
same latent bug.

### Naive chase AI does not survive a segmented map (fixed for Zombie 2026-09-01)
Segmenting Zombie's map into zones broke its zombie AI three separate ways, each of which looked
like a different bug. Worth knowing before any other game gets interior walls:

1. **Beelining** jams a zombie against a boundary wall a few hundred px from the nearest opening,
   permanently. Wall-following heuristics got most of the horde through and reliably stranded the
   rest, which is worse than a slow round — it means the round never ends.
2. **The nav grid sampled passability at each cell's centre**, so a 20px wall falling in the gap
   between two adjacent cell centres was *invisible* to the pathfinder. The flow field ran
   straight through solid geometry and steered zombies confidently into walls. Test the WHOLE
   cell, padded by half an entity.
3. **Off-field recovery must be line-of-sight checked.** An entity pressed flat against a wall
   sits in a cell the BFS never reached; recovering by "nearest cell with the lowest distance"
   happily picks one on the far side of a closed door 20px away.

The fix is a BFS flow field (multi-source from every player, so zombies chase the nearest player
*by path*, not by straight line). It's cheap — 120x68 cells, refreshed every 220ms — and it has no
stuck state to escape from.

### Pathfinding bugs that look like three different bugs (Zombie, 2026-09-02)
Adding interior geometry to Zombie broke its flow-field navigation four more times, each with a
different signature. All four are generic to any grid-pathfinding game and worth knowing up front:

1. **Nav resolution vs. smallest opening.** A gap only *guarantees* a nav cell at
   `2*CELL + 2*pad` — cell size, padding each side, plus up to a whole cell lost to alignment. At
   `CELL=40` the threshold was 96px, so 46px nook holes and 70px doorways were **walkable in fact
   but sealed to the pathfinder**. Shrink `CELL` or widen the opening; never assume "it fits".
2. **Diagonal corner-cutting → invisible oscillation.** Picking a diagonal neighbour that is open
   while the corner between is not makes an entity walk at an unreachable target, slide off,
   return, and repeat *forever while moving every frame* — so stuck-detection never fires. Require
   both orthogonal neighbours to be passable. **This was the real bug behind three earlier rounds
   of "wall-following" fixes that each only moved the number a little.**
3. **Cover geometry boxing in corners.** Decorative wall spurs near a T-junction can enclose a
   pocket nothing can path into. Clip them well clear of intersections.
4. **Escape hatches must sit at the right point in the if/else chain.** A "stuck for 4s → relocate"
   branch placed after a `slideHold > 0` branch was unreachable, because slideHold re-armed every
   30 frames.

Generalisable: **when a heuristic fix moves the number but doesn't fix it, stop adding heuristics
and instrument the actual failure.** Printing one stuck entity's `stuck` counter (max 5, not 240)
is what finally revealed it was oscillating rather than wedged.

### Two JS footguns that cost real time here (2026-09-02)
- **`if (arr[0])` on an index that can legitimately be 0.** Zone 0 is a real zone; a truthiness
  check silently dropped a weapon from the map on 7 seeds in 40. Use `!== undefined`.
- **`String.replace(old, new)` replaces ALL occurrences.** A patch meant for `hostHandleBuy`
  landed in `applyPurchase` too, where the validation code returned early *and* deducted the cost
  a second time — so purchases charged double and granted nothing. Assert the occurrence count.

### `python -m http.server` serves stale JS and silently invalidates local test runs
It sends no `Cache-Control`, so browsers apply *heuristic freshness* and re-serve cached scripts
**without revalidating** even after the file changes on disk. Several Zombie test runs executed
old code and produced confident, wrong results — including one "6/6 layouts pass" that was
measured against a stale pathfinding grid. Every game in this repo is a static file tested this
way, so this can bite anywhere. Use a no-store handler when iterating
(`scratchpad/nocache-server.py`), and when a result looks impossible, check the loaded source
first: `someFunction.toString().includes('<new code>')`.
